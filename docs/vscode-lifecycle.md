# Preview lifecycle

The extension has three owners: the host owns the captured input and its confirmation, the webview owns computation and recovery, and the shared view owns DOM presentation and reading positions.

The webview keeps two concurrent records. `capture` contains the host epoch, the attempted snapshot and input work (`reading`, `computing` or `idle`). A computing record owns its worker and timeout. `screen` is `empty`, `candidate`, `restoring`, `visible` or `stopped`; its `good` value is the only client record of a successfully presented snapshot. Reading new input can overlap restoring an older view, so these concerns remain separate.

A worker result is a candidate. The shared view calls `onPresented` once after mounting, alignment and any bookmark restoration. Only then does the webview promote the candidate, update its provenance and acknowledge the host. Later settled page, prefix and resize changes use `onViewStateChanged` to save position. They cannot confirm another snapshot. The shared view samples its bookmark once and passes it to either callback. All bookkeeping completes before the callback, so a callback may reset or replace the view without stale work running afterward.

A presentation failure restores the last good result from a safe starting position. Failed restoration clears the display and cancels work, so an already queued worker reply cannot revive it. Explicit recapture permits another attempt. The attempted-snapshot latch suppresses repeated attempts within a host epoch, including error messages replaying an older confirmed input.

Scroll events schedule one save after 200 ms. Settled view changes, opening Source and page exit flush the current position immediately. Position is associated with the displayed snapshot, never a pending candidate. Disposal releases that displayed state before clearing DOM, preventing a later callback from overwriting the final bookmark.

Each view owns its settled bookmark. `show(mode, bookmark)` validates a saved bookmark when creating that view; `getState()` reads the active, presented view's position with its last settled pages. The webview alone wraps this in the existing saved-state format. The website retains its per-mode DOM and pixel scroll positions without reading or maintaining a separate bookmark map. Error handling, reset and normal pause share one cancellation routine; pause alone records heights and pixel position for a view that will be reused. Reset discards views without measuring them.

Hidden previews retain VS Code's default disposal lifecycle. Keeping them alive could avoid ordinary return reconstruction at a memory cost, but it would not remove explicit-reload recovery. That policy and Refresh starting at the top are unchanged. Loaded content is retained for selection and navigation.

## Verification

The refactor preserves the existing host, website and preview behavior checks. Added cases cover one confirmation through page/resize/batch changes, reset without discarded-row measurements, reentrant callbacks, terminal rollback with overlapping computation, and immediate reload, Source navigation and page exit.

An independent review also found a pre-existing website race: a pending GitHub version request could replace a newer local file, draft edit or swap. A separate fix invalidates pending version work when those local actions take ownership, without clearing loaded history. Three deferred-network browser regressions fail before the fix and pass afterward.

The queued-result case failed before the ownership change: a newer worker could repopulate the DOM after failed rollback. It passes when terminal recovery invalidates the computing record. A separate pair of regressions reproduced premature restored metadata and a double rebuild during Refresh; both pass after the local recovery cleanup. No existing outcome assertion, restore threshold or timeout was relaxed.

The final local suites pass 96 Node and 37 website-browser tests, plus 28 extension Node and 58 bundled-preview tests (counts overlap). Installed acceptance passes 28 checks each on VS Code 1.146.0 and 1.85.0, plus seven each in Restricted Mode and a read-only virtual workspace. All four runs use one VSIX, SHA-256 `28c618bb96c1e02715b29422190ef569f2fb8dfbe17e3fb8d22e96c95d0e08b0`, with matching loaded runtime and harness hashes. Their 46 automated accessibility states have zero violations or incomplete checks. Raw results live in ignored `artifacts/lifecycle-r4-ide-*/`. The first minimum-version attempt stopped before extension activation when the title-action click was intercepted; the unchanged repeat passed. That first attempt is retained separately and is not counted as a successful run.

Before the final view-owned bookmark simplification, a five-pair alternating browser probe compared scroll-frame saving with the 200 ms timer over 600 visited paragraphs. Each trial scrolled for 180 frames and checked the final snapshot, pages and anchor. Saves and hit tests fell from 180 to 14 per trial, with zero final anchor error in all ten runs. This measures removed persistence work in the browser harness, not native IPC or user-visible latency. Input limits, construction budgets and retained-DOM growth remain unchanged.

The final package also has five warm Refresh trials per workload on each installed version, with a separate profiling trial excluded. Current VS Code medians were 138.3 ms for a 1,200-row table, 153.5 ms for 100 prose sections and 626.9 ms for 50,000 code lines; their trial ranges were 126.9–152.5, 152.2–160.7 and 594.9–690.4 ms. VS Code 1.85 medians were 219.7, 267.5 and 1037.3 ms, with ranges 215.9–221.6, 252.8–272.1 and 1016.9–1068.3 ms. Each trial checks output and measures click-to-initial-presentation, including reads, worker, transfer and DOM work. These are warm observations on one Mac with other applications active, not comparative speedups or measurements of complete traversal, cold start or peak memory.
